A · kohaku 原作天然分支扫描

我重读了 kohaku 原作中文翻译 (来源: CSC · 琥珀の牢) 的全文 638 行. 不是线性单线本, **作者埋了 6 个明确分歧点 + 至少 5 种结局组合**.

A.1 6 个分歧点 (原文标注的)

  • 1救不救伊藤? (line 180 作者明示)
    原文: "这里就是要决定要不要救伊藤的分歧点". 救了 → 伊藤陪你到终局, 能开直升机. 不救 → 后期回头 → 伊藤已被杀.
  • 2穿不穿防护服探索?
    原文 line 170-176: 穿了 → 几乎不被发现, 但身体技能 -10%. 不穿 → 容易被识破触发警报. 防护服只有 1 套.
  • 3研究所探索顺序 (开放沙盒)
    仓库 / 病毒培养室 / 样本保管库 / 药剂室 / 研究办公室 / 生体实验室 / 宿泊室 / 资料室 — **8 个房间任意顺序**, 每个有不同检定 + 收益. 玩家可能只去 3 个, 也可能 8 个全去.
  • 4蛇人 boss 战: 打 vs 偷溜
    原文 line 506: "如果调查员不打倒蛇人、而是想直接逃走, 就跳到描写部分". 打 → 拿到密码纸条. 偷溜 → 触发"伊古"召唤, 巨型蛇怪追击. 走法完全不同.
  • 5是否启动自爆?
    原文 line 588-590: "不启动自爆装置直接逃跑 → 不管从哪边逃, 都会出现大量蛇, 调查员会被蛇攻击致死". **不启动 = 强制 BAD END**.
  • 6逃跑路径: 屋顶直升机 vs 1 楼
    屋顶: 需要伊藤 (或写日记的所员) 会开直升机. 1 楼: 撑过 2 轮蛇攻击 + 出门遇丧尸 (需"死之粉"否则死).

A.2 结局组合矩阵

★★★ HAPPY END (带抗体疫苗资料脱出)

条件: 自爆 + 屋顶/1楼脱出 + 拿到 hasVaccineData==true 或 hasZVirusData==true

SAN 恢复 1D10. 世界被拯救.

★★ NORMAL END (没带资料脱出)

条件: 自爆 + 屋顶/1楼脱出 + 没拿到关键资料

SAN 恢复 1D6. 抗体被找到, 世界慢慢拯救.

★ BAD END · 蛇咬死 (1 楼路线)

条件: 选 1 楼路线 + 撑不过 2 轮蛇攻击

★ BAD END · 丧尸咬死 (1 楼出门)

条件: 1 楼到达地面 + 没带死之粉

★ BAD END · 没启动自爆

条件: 没按自爆装置直接逃 → 蛇围攻

★ BAD END · 屋顶但无人开机

条件: 屋顶路线 + 伊藤死 + 没救所员

SAN 还有 4 个独立加成: 带伊藤回去 (+1D3) / 带所员回去 (+1D3) / 救生体实验室人质 (+1D3) / 带 Z 病毒资料 (+1D3).

原作扫描结论

琥珀の牢**本身就是真分支多结局本子**. 我们 V0 parser 砍成 5 场景线性是"压缩 10.8 倍"的副作用, 不是原作没分支. 同样道理, Chaosium 官方 1 人本 Alone Against the Flames 有 270 个探索段 + 18 种结局 (Chaosium 官方数据).

意味着: V2 P1.B 的工作不是"凭空造分支", 是"识别 + 还原原作分支". 这降低了 LLM 风险.

B · 业界主流分支设计套路

套路 代表作 / 工具 分支方式 状态系统 典型规模
纯 CYOA (Choose Your Own Adventure) Bantam 80 年代系列 / AAtF / Lone Wolf 段落编号, 每段 2-3 个选择跳到不同段 几乎无 (有少量物品标记) 200-400 段 / 10-25 结局
Ink (inkle 公司) 80 Days / Heaven's Vault / Sorcery! 文本 DSL 写流程, 嵌入 {if} 条件 / 变量 / 跳转 完整 (booleans / counters / lists) 10k+ 段, 复杂 NPC 状态网
ChoiceScript (Choice of Games) Choice of the Dragon / 大量商业短篇 命令式语法, 每个章节 1-2 个 *choice 节点 完整 (角色属性 + flags) 50-200 章节 / 4-12 结局
Twine 独立 IF 创作社区 可视化节点编辑, 节点间画线 中等 (扩展库) 跨度大 (30-1000 节点)
视觉小说 / Galgame (NVL/ADV) Fate / 月姫 / Steins;Gate 主线 + 1-3 个角色线分歧, 通常**flag 后期影响** 完整 (大量 flag, 攻略性强) 20+ 小时游玩 / 5-10 个结局

关键洞察

纯 CYOA 状态系统最简, 但分支爆炸难管理 — 作者要画大图. AAtF 走这套.

Ink / ChoiceScript 有完整变量系统, 适合"状态影响远端剧情" (我们 V2 想要的). Sorcery! 这种 3-4 个状态 (健康/胆量/技巧/...) + 几十个 flag 撑起一整个三部曲.

Galgame 套路 经典是"主线大致一致, 分歧点设在关键时机, 累积 flag 决定后期女主线". 我们做 1 人本不全照搬, 但"主线 + 几个关键岔口"的轻分支模式适合 V2.

C · 4 条技术路线 (用什么方式造分支)

路线 作者要做的事 AI 做的事 质量稳定性 规模化 用户场景
路线 1 · 全手工 写完整 scenario.json (含 exits / flags / endings 全标好) 不参与, 只渲染 narrate 最高 — 作者意图百分百 慢 — 一本 1-3 天 专业作者 / 高质量发布
路线 2 · LLM 抽取已有结构 提供原作 + 让 AI 找分支 读原作 + 抽取已有分歧点 + 标记 flag 高 (原作有什么 AI 抽什么, 不发明) 快 — 1 本 < 1 小时 ★ 改编现有跑团本 (我们这种)
路线 3 · LLM 增强 提供原作 + 给"在 X 处加 Y 分支"指令 读原作 + 按指令插入新分支 + 平衡 flag 中等 — AI 可能加得不自洽 快 原作太短 / 想加重玩价值
路线 4 · LLM 全自动 只给主题 / 风格指令 完全自由编 (结构 + 内容) 最低 — 玩起来像 AI Dungeon 最快 不在乎跑团真实感 / 大量量产

我推荐: 路线 2 (LLM 抽取已有结构)

我们这个项目的核心定位是"AI 改编现有跑团本" (V1 source L2 选择). 原作有的分支必须保留, AI 不能瞎加. 路线 2 让 AI 做"识别已有"而不是"创造新"的工作, 风险最低.

具体: V1 parser 已经能切段保留 originalText, V2 P1.B 让 parser 多做一步 —— 抽取原作每段的"如果调查员选 X 还是 Y" 决策点, 输出到 scene.exits[] 含 sets/requires, 输出到 scenario.endings[]. AI 不发明原作没有的分支.

D.2 parser V2 的 prompt 改造 (核心)

给 LLM 的提示框架 (按 6 步):

1. 你看完原作, 找"明示分歧点": 原文出现"是否 X / 选择 Y" 措辞
2. 找"隐含分歧点": 同一场景有多种可能行为且后果不同
3. 找"作者埋的开放沙盒": 多房间任意顺序探索类
4. 提取"状态依赖": 后期场景 narrate 提到"如果前面做了 X" 的引用
5. 提取"结局组合": 原文【结局】章节列出的所有结局变体
6. 输出严格 JSON: scene.exits[] 含 requires/sets, scenario.endings[] 含 conditionExpr

★ 绝对禁止: 发明原作没有的分支 / 决策点 / 状态.
★ 不确定的分支: 标 confidence=low, 不要硬塞.

D.4 验证机制 (gate)

LLM 输出后必须过 4 个 sanity check, 不过就报错给用户手工修, 不直接 deploy:

Gate检查什么失败怎么办
G1 · 可达性 从 startSceneId 起 BFS, 每个 scene 都能达到. 没有"孤岛" 报告无法到达的 scene, 让用户检查 exits
G2 · 至少 2 条不同路径 枚举所有从 start 到 ending 的路径, ≥ 2 条 报告分支太少, 让 LLM 重新挖或用户手补
G3 · 至少 2 个结局可触发 枚举每个 ending 的 conditionExpr, 至少 2 个有可达组合 报告无法触发的 ending, 提示 flag 缺失
G4 · 没有死循环 每个场景有出口 (或是 ending), 没有 A→B→A 循环 报告循环路径

E · 推荐实施路线

阶段做什么耗时风险
Stage 1 · 手工跑通 我手工把 kohaku.v1.scenario.json 扩成 v2 (按 D.3 图), 跑全栈验证整套 V2 引擎工作 1-2h 低 — 不依赖 LLM

Stage 3 · 在 kohaku 跑 parser V2 对比 LLM 输出 vs Stage 1 手工版, 看 LLM 能找出多少分支 1h 低 — 有 baseline 比较
Stage 4 · 拿别的本子验证泛化 找另一本日文 1 人本, 跑 parser V2, 看输出质量 2h + 等用户找本子 中
Stage 5 · 如果 LLM 跑得糊涂 fallback 到半自动模式: parser 给草稿 + UI 让作者手工调 1 天 低

F · 你拍板

3 个选项:

选 ① · 走 Stage 1 → 2 → 3 顺序

我先手工扩 kohaku.v2 让你立刻能玩出真分支 (1-2h), 然后再做 parser 自动化. 推荐路径, 风险最小.

选 ② · 直接做 parser V2 跳过手工

我直接改 parser, 让 LLM 一次性产出 kohaku.v2 含分支. 快但风险高, LLM 可能产出不自洽的分支图.

选 ③ · 你说别的方向

例如: "我想要 kohaku 这个本就用手工", "未来新本子才用 parser auto"; 或 "先做 G1-G4 验证器再说"; 或 "你写完 D.2 prompt 给我看了再动".
